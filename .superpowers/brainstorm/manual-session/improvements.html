개선 제안 사항

현재 구상에서 고려해볼 3가지 포인트

1. 라우팅 충돌 위험

현재 구상 — 충돌 가능성
spinetrack.ai/ → 랜딩 페이지
spinetrack.ai/P001 → 환자 대시보드
spinetrack.ai/about → 소개 페이지?
spinetrack.ai/pricing → 가격?
⚠️ /about 과 /P001 이 같은 [slug] 라우트를 공유
→ 환자 ID가 페이지명과 겹치면 충돌
대안 — 서브도메인 분리
spinetrack.ai/* → 랜딩 + 마케팅 페이지
app.spinetrack.ai/P001 → 환자 대시보드
dashboard.spinetrack.ai/ → 관리자
✓ 각 도메인이 독립적 → 충돌 없음
✓ 환자 QR: app.spinetrack.ai/P001

2. 데이터 레이어 — 가장 큰 과제

현재: localStorage 기반 → 관리자 대시보드 불가능
환자 브라우저
PROM, 접속 로그, 체크리스트
모두 localStorage에 저장
✕
관리자 대시보드
환자 데이터에 접근 불가
localStorage는 브라우저 격리
필요한 것: 서버 사이드 데이터베이스 (Cloudflare D1, Supabase, 등)
→ 환자가 PROM 제출 시 서버에 저장 → 관리자가 조회 가능

3. 프로젝트 구조: 모노레포 vs 멀티레포

A

모노레포 (Turborepo)

apps/landing + apps/patient + apps/admin

장점

  • 타입/유틸 공유 쉬움
  • 한 번에 배포 관리
  • 코드 일관성

단점

  • 초기 셋업 복잡
  • 빌드 시간 증가
B

단일 Next.js 앱 확장

현재 프로젝트에 랜딩 + 관리자 라우트 추가

장점

  • 기존 코드 그대로 활용
  • 셋업 비용 최소
  • Vercel 하나로 배포

단점

  • 앱이 커지면 복잡도 증가
  • 서브도메인 라우팅 별도 설정
C

멀티레포 (별도 프로젝트)

랜딩/환자/관리자를 각각 독립 레포로

장점

  • 완전한 독립 배포
  • 팀 분리 시 유리

단점

  • 타입/컴포넌트 공유 어려움
  • 일관성 유지 힘듦
  • 관리 포인트 3배

내 추천

B (단일 앱 확장)을 추천합니다. 이유:

  • 혼자 개발하는 프로젝트에서 모노레포/멀티레포는 오버엔지니어링
  • Next.js의 미들웨어로 서브도메인 라우팅 처리 가능
  • 기존 코드, 타입, 컴포넌트를 그대로 재사용
  • 나중에 커지면 그때 분리해도 늦지 않음

단, 서브도메인 분리(app.spinetrack.ai)는 강력 추천 — 라우팅 충돌 방지 + 깔끔한 구조
